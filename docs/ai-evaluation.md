# Saved-output evaluation and evidence review

This phase delivers an offline evaluation harness and candidate evidence
corrections. It does not establish live provider quality, integrate platform
login/offers, enable matching or send applications.

## Run the offline baseline

The checked-in corpus has 20 synthetic French/English cases, split into 10
development and 10 held-out cases. It covers CV extraction, dossiers/letters,
retrieval citations and keyword memory. Cases include missing facts, unrelated
quotes, negation, ambiguous dates, conflicting preferences/requirements,
multilingual aliases, prompt injection, invented company facts and provider
refusal/unavailability outcomes.

The accompanying saved run contains deliberately good and bad **synthetic
responses**, not output from Groq or Gemini. Its purpose is to expose validation
blind spots and exercise scoring. The corpus expectations are provisional,
assistant-authored examples; they have not been human-labelled or independently
validated. These small partitions bootstrap the workflow, not a statistical
benchmark. Do not tune prompts against the held-out partition when collecting
real evaluation runs.

```powershell
uv run python -m app.evaluation.cli score --outputs data/evaluation/synthetic-baseline-v1.json --out .artifacts/evaluation/baseline-v1.json --markdown .artifacts/evaluation/baseline-v1.md
uv run python -m app.evaluation.cli init-review --outputs data/evaluation/synthetic-baseline-v1.json --out .artifacts/evaluation/reviews-v1.json
```

The CLI needs no credentials, database, model download or provider call. It scores
saved JSON and writes JSON/Markdown artifacts. Keep real personal data out of
checked-in datasets; review any real output artifacts under the chosen retention
policy. The harness does not generate new outputs or infer actual provider retries.
Saved refused/unavailable outcomes test outcome accounting only.

## What the report measures

Deterministic output checks and provisional reference comparisons are separate
from human judgments. The report keeps development/held-out partitions separate:

- CV: schema/quote grounding, matched/extra/missed facts, precision/recall and
  dropped facts. A fact quoted from an instruction or negation can still pass
  grounding; the reference expectation can flag the resulting extra fact.
- Dossier: existing quote checks, false supported-labels against provisional
  expectations, missed/extra/duplicate requirements and assessment accuracy.
  Forbidden letter phrases flag specifically authored examples of fabricated
  claims; they are not a general semantic factuality detector.
- Retrieval: supplied citation IDs, reference relevance precision/recall against
  provisional expected IDs. Valid IDs do not establish sentence-level support.
- Memory: the production keyword filter and retention of explicitly forbidden
  synthetic names, contact details or superseded terms. This does not provide a
  general identity classifier.
- Outcomes: success/refusal/unavailability matches and output-validation errors.
  Invalid citations are reported as invalid output even when the JSON is valid.

Zero-denominator rates are `null`. Human writing scores stay `null` until supplied;
blank review templates contribute zero completed reviews. Reports always state
`release_gate: not_assessed`. Passing harness tests means the scoring and review
mechanics work, not that a model meets a quality threshold.

## Record saved outputs with provenance

Use `data/evaluation/synthetic-baseline-v1.json` as the format example. A saved run
must contain every corpus case exactly once. Record provider, model, whether the
run is synthetic, generation parameters, prompt fingerprints for all workflows
and the reference snapshot identifier. Configuration has a bounded schema and
does not accept API keys or arbitrary environment settings.

`corpus_sha256` and each `case_sha256` are SHA-256 of canonical JSON generated by
`app.evaluation.models.fingerprint`: keys sorted, UTF-8, no unnecessary whitespace,
non-ASCII characters preserved. Prompt hashes in the supplied fixture use the
actual prompt string's UTF-8 bytes. Record the prompts used for a new run, even if
they differ from today's source. Do not copy current hashes onto older outputs.

Success results contain the returned output object; refused/unavailable results
must have `output: null`. CV outputs match `Extraction`, dossiers match `Dossier`,
retrieval matches `Answer` and memory matches `ContextDecision`. Each case's
sources/references are in the corpus. Unknown/duplicate/missing cases, changed
inputs and mismatched corpus hashes are rejected. JSON whitespace changes do not
invalidate canonical fingerprints.

## Human-review procedure

Open the corpus and saved outputs alongside the generated review template.
Review **all emitted claims**, rather than only accepting the provisional labels.
Use two reviewers and resolve disagreements before making a product-quality
decision; the harness currently records one attributed judgment per output, so
keep separate reviewer artifacts until adjudication.

Fill `reviewer` and the workflow's required fields:

| Workflow | Required human ratings |
| --- | --- |
| CV | `extraction_accuracy`: correct / mixed / incorrect |
| Dossier | `claim_support`: supported / mixed / unsupported; `letter_factuality`: faithful / unsupported / contradictory; `writing_quality`: integer 1–5 |
| Retrieval | `sentence_support`: supported / mixed / unsupported; `writing_quality`: integer 1–5 |
| Memory | `memory_privacy`: safe / identity_leak |

“Supported” requires the quote to substantiate the claim, including negation and
conflicts; occurrence alone is insufficient. “Faithful” requires every factual
letter claim to come from supplied sources. “Sentence support” requires each
factual sentence to be supported by the cited reference. A superseded preference
is a memory regression in provisional metrics even if it is not an identity leak.
Writing: 1 is unusable, 3 needs substantive editing, 5 is clear, relevant and
natural in the requested language. Use notes to explain errors/disagreements.
These judgments assess source support, not verified real-world competence.

```powershell
uv run python -m app.evaluation.cli score --outputs data/evaluation/synthetic-baseline-v1.json --reviews .artifacts/evaluation/reviews-v1.json --out .artifacts/evaluation/reviewed-v1.json --markdown .artifacts/evaluation/reviewed-v1.md
```

Reviews are bound to the exact run and output hashes. Scores without attribution,
incomplete attributed reviews, ratings for a different workflow, duplicate reviews
and stale/cross-run annotations are rejected. Human counts/judgments are reported
separately and never replace provisional metrics. Even a fully reviewed run keeps
the release gate unassessed until the product owner defines acceptance thresholds.

## Correct a dossier's evidence

```http
PUT /api/v1/application-drafts/{draft_id}/evidence
Content-Type: application/json

{
  "expected_version": 1,
  "evidence": [{
    "requirement": "Kubernetes",
    "job_quote": "requiring Kubernetes",
    "candidate_quote": null,
    "assessment": "not_evidenced"
  }],
  "reason": "The quoted Python project does not establish Kubernetes experience."
}
```

Supply the complete existing evidence list in its original order. Requirement/job
quotes are immutable; the candidate can change assessments and candidate quotes.
Supported quotes must occur in the pinned profile snapshot. `not_evidenced` requires
a null candidate quote. Source changes require a new dossier. Missing requirements
cannot be added through this endpoint; regenerate against corrected source text.
Human correction remains an assertion and does not certify semantic truth.

Only the owning authenticated candidate can edit a completed dossier at the exact
current version, with the original profile still accepted at that version. The
operation increments the draft version, stores immutable history and the reason,
marks `analysis_review.kind: candidate_corrected`, clears approval and emits a
`draft.evidence_corrected` event. Initial model output stays in version 1, with
`analysis_review.kind: model_proposal` for new dossiers. Existing dossiers without
that metadata remain correctable; no schema migration is required.

Evidence changes do not rewrite the cover letter. `analysis_letter_version` becomes
null, so the client must review the letter for remaining unsupported claims and
edit it through the existing endpoint as needed. New approval binds the corrected
analysis, its review provenance, the letter, source versions/hashes and destination.
An old approval becomes inactive. Concurrent edits/approval and history failures
are protected by the existing transaction/version guards. Nothing is submitted.

Errors include 404 for unknown/other-user records, 409 for stale versions or
unavailable dossiers/profile versions, and 422 for invalid evidence, changed job
requirements or trusted metadata supplied by the client.
